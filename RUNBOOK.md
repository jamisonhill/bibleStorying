## §0 — Covering for me (start here)

- **What this project is, in one sentence:** A free phone app (iPhone + Android) that
  carries the Bible stories from biblestoryingkenya.com so pastors in Kenya can read
  and play them without internet.
- **Does anything real depend on it?** A ministry client is counting on it, but as of
  this pause it is in beta testing — not yet in the app stores. Nothing breaks for
  anyone if it sits untouched.
- **Is it currently running / live?** The app is only on test phones. The content
  pipeline IS live: a GitHub Action updates the story bundle daily (§8).
- **Deploy a fix:** see §7.
- **If you only do one thing:** nothing. It is safe to leave alone; the daily job
  fails safe (it publishes nothing rather than something broken).
- **When in doubt:** §3.

## §1 — Likely events & responses

| If this happens | Do this |
|---|---|
| A GitHub issue appears titled "Content crawl failed …" | The website's page layout changed. Fix the parsers in `pipeline/src/parse.ts` (tests + fixtures in `pipeline/test/`), or disable the schedule in `.github/workflows/content-update.yml` and let the app keep serving its last-good content. |
| The ministry updates stories on the website | Nothing to do — the daily job picks it up and phones update themselves within ~a day of being online. |
| Someone wants the app in the app stores | Follow the publishing checklist in `README.md` (needs the client's Apple/Google accounts). |
| The client's own developer accounts are ready | Change `bundleIdentifier`, `android.package`, and `appleTeamId` in `app/app.json` before first store upload. |

## §2 — Do NOT touch

- `content/`, `app/src/content/`, `app/assets/content/` — generated by the pipeline
  and seed script. Hand edits are overwritten and can corrupt the update chain.
- The GitHub Pages URL scheme — installed apps poll `manifest.json` at the published
  URL. If hosting must move, publish one last manifest at the old URL or ship an app
  update with the new `DEFAULT_CONTENT_BASE_URL` (`app/src/lib/updater.ts`).
- The `content-update.yml` fail-loud behavior — do not make the crawler "best effort";
  publishing a half-parsed bundle is worse than publishing nothing.

## §5 — System map

```
biblestoryingkenya.com (ministry's website, source of truth)
        │ daily crawl (GitHub Action)
        ▼
pipeline/ → content/ bundle (committed) → GitHub Pages (manifest.json)
        │                                        │
        │ bundled at app build time              │ polled ~daily by installed apps
        ▼                                        ▼
app/ (Expo) ──────────────────────────► phones (text/images offline;
                                         audio downloaded from the website itself)
```

- **Data flow:** all content originates on the ministry's website; the app stores no
  user data and sends nothing anywhere. Audio files are fetched directly from the
  website's own hosting.
- _Last verified: 2026-08-30_

## §7 — Deployment

**Content** deploys itself (§8), or manually: Actions → "Update content bundle" → Run
workflow. **App code:**

1. `cd pipeline && npm ci && node src/build.ts` (refresh content if needed)
2. `cd app && npm ci && npm run seed`
3. Test build to a connected iPhone: see `.planning/RESUME.md` for the exact
   xcodebuild command; Android: `npx expo run:android`.
4. Store releases: `eas build --platform all` then `eas submit` (blocked on client
   accounts — README checklist).
- **Rollback (content):** `git revert` the offending `content:` commit and re-run the
  workflow; phones reconcile to whatever the manifest says.
- _Last verified: 2026-08-30_

## §8 — Scheduled processes

| Job | What it does | Scheduled where | When | If it stops |

## §13 — Known quirks & gotchas

- Expo Go on the iOS App Store is stuck at SDK 54; this app is SDK 57 — physical
  iPhone testing requires a real native build, not Expo Go.
- The website is hand-edited; two Borana stories legitimately have no text (audio/doc
  only) and Sonship Maasai/Borana pages are empty placeholders. The parsers allow this.
- A few stories share one cloth-art image; cross-language linking disambiguates with
  `#n` suffixes (`bsk_3`, `bsk_3#1`). Don't "simplify" that.
